# Feature Review

현재 브랜치에서 **아직 커밋되지 않은 변경사항**을 대상으로, 사용자가 지정한 "기능"과 관련된 부분만 골라내어 실무 프론트엔드 코드 리뷰 관점으로 리뷰한다. **파일을 절대 수정하지 않는다. 리뷰만 한다.**

인자로 받은 기능명(예: "회원가입 기능")은 리뷰 범위를 좁히는 필터로 사용한다. 인자가 없으면 커밋되지 않은 변경사항 전체를 리뷰 대상으로 한다.

## 1단계 — 커밋되지 않은 변경사항 확인

브랜치 비교(origin/main, main 등) 없이, 아래 두 명령만으로 충분하다.

1. `git status --short` 로 수정된 파일과 untracked 파일 목록을 확인한다.
2. `git diff HEAD` 로 추적 중인 파일의 미커밋 변경 내용(staged + unstaged)을 확인한다.
3. untracked 파일은 `git diff`에 잡히지 않으므로, 기능명과 관련돼 보이는 untracked 파일은 Read 도구로 직접 내용을 읽어서 리뷰 대상에 포함한다.

## 2단계 — 리뷰 대상 필터링

사용자가 기능명을 지정한 경우, 변경된 파일 목록에서 해당 기능과 관련된 파일만 골라낸다. 판단 기준:

- 파일/폴더 경로, 컴포넌트명, 훅 이름 등에 기능명과 관련된 키워드가 포함되는지
- diff 내용(주석, 문자열, 함수명, JSX 텍스트 등)에 기능 관련 맥락이 있는지
- 애매하면 관련 가능성이 있는 파일은 포함하되, 리뷰 시작 부분에 "이 파일들은 관련성이 확실하지 않아 포함/제외했다"를 명시한다.

기능명이 없으면 전체 diff를 리뷰 대상으로 한다.

## 3단계 — 리뷰 기준

아래 관점으로 코드를 실제로 Read해서 검토한다 (diff만 보지 말고 필요하면 파일 전체를 읽어서 문맥을 파악한다):

- 기능 요구사항을 코드가 잘 만족하는지
- 컴포넌트 분리와 책임이 적절한지
- 상태 관리 방식이 과하지 않은지 (불필요한 전역 상태, 과도한 useState/useEffect 등)
- API 호출 위치와 비동기 처리 방식이 적절한지
- TanStack Query 사용 시 mutation, queryKey, cache invalidation/무효화 처리가 적절한지
- form validation, loading/error/success UX가 갖춰져 있는지
- 타입 안정성 (any 남용, 타입 단언, optional 처리 등)
- 불필요한 중복 코드나 과한 추상화가 있는지
- 접근성(a11y), 보안(XSS, 민감정보 노출 등), 성능(불필요한 리렌더링, 큰 번들 등) 관점에서 아쉬운 점
- 실무 유지보수 기준에서 고치면 좋은 점
- 변경 규모가 한 커밋에 적절한지, 성격이 다른 변경(기능 + 리팩토링 + 포맷팅 등)이 한 덩어리로 섞여 있지 않은지

## 4단계 — 출력 형식

아래 순서/제목을 기본 틀로 하되, **내용이 없는 섹션은 제목째로 생략한다** (빈 섹션이나 "특별히 없음" 같은 채우기용 문장을 쓰지 않는다). 각 섹션은 근거 없는 칭찬이나 형식적인 코멘트를 나열하지 말고, 실무 기준에서 구체적으로 작성한다. 문제점은 반드시 파일명(및 가능하면 라인)과 이유를 함께 제시한다. 코드 예시는 고치는 방향을 보여줄 필요가 있을 때만 짧게(핵심 부분만) 제시한다. 큰 리팩토링 제안은 지양하고, 현재 구현 흐름 안에서 개선 가능한 범위로 제안을 한정한다.

```
## 1. 기능 변경 요약
(리뷰 대상이 된 파일 목록과 변경 내용을 간단히 정리)

## 2. 전체 평가
(1~2문장 총평)

## 3. 아쉬운 점
(파일명 + 이유. 실무 기준으로 구체적으로. 없으면 섹션 자체를 생략)

## 4. 반드시 고치면 좋은 점
(머지 전에 고치는 게 좋은 항목만. 파일명 + 이유 + 필요시 짧은 코드 예시. 없으면 섹션 자체를 생략)

## 5. 선택적으로 개선하면 좋은 점
(급하지 않지만 있으면 좋은 항목. 없으면 섹션 자체를 생략)

## 6. 최종 판단
- 머지 가능 / 수정 후 머지 권장 / 구조 재검토 필요 중 하나를 선택하고 한 줄로 이유를 덧붙인다.

## 7. 커밋 분리 제안
(미커밋 변경을 커밋 단위로 나눈다. 커밋마다 포함 파일과 한 줄 메시지 `<type>: 명령형 요약`을 항상 제시한다. type은 feat / fix / refactor / chore / docs / style / test / perf / build / ci 중 하나. "왜"가 제목만으로 드러나지 않는 커밋에만 본문(제목 아래 빈 줄 + 이유 문단 + `-` 불릿)을 덧붙인다. 변경이 단일 성격이면 커밋 1개로 제시한다. 이번 작업과 무관한 변경은 별도 항목으로 분리해 안내한다.)
```

## 주의사항

- 절대 파일을 Edit/Write로 수정하지 않는다. 오직 Read, Grep, Glob, Bash(git 조회 명령)만 사용한다.
- git 조회 이외의 상태 변경 명령(add, commit, push, checkout, reset 등)은 실행하지 않는다.
- diff가 비어 있으면(변경사항 없음) 그 사실을 그대로 알리고 리뷰를 생략한다.
- 지정한 기능명과 관련된 변경사항을 diff에서 전혀 찾지 못하면, 그 사실을 알리고 전체 diff 중 관련 가능성이 있는 파일이 있는지 다시 한 번 확인해서 안내한다.
